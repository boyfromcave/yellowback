## 1. Finding

**Quadratic overlay copy (W3-V-4).** `VaultState::ApplyTx` (`ycash-dd/src/vault/state.cpp:370-379`) constructs `VaultState child(*this)` — a copy of the **whole** block overlay `changes` (`std::map<std::string, std::optional<std::string>>`, `state.h:422`) — for every transaction, applies the transaction to the child, and on success merges every child entry back (`MergeFrom`, `:349-352`). `ApplyBlock` (`:381+`) calls it for every transaction of the block in the sequential phase of `ConnectBlock` (after `control.Wait()`, `src/main.cpp:3478-3493`); the miner's running trial does the same per candidate (`src/miner.cpp:585`; ycash6 `TemplateRun`, `src/vault/node.cpp:326-343`). With `T` state-changing transactions each touching distinct keys the work is `Σ i ≈ T²/2` map-node copies — ≈ 32 M for `T ≈ 8,000` (a 2 MB block of ~250-byte heartbeats or V creations over many cheap OPEN sets with 1-zat `bondMin`), several seconds of allocation-bound work on every node for a valid block. Not a split, not an unbounded stall; it inflates validation time predictably.

**No consensus sigop cost for the new signature opcodes (W3-V-6, 01/N-1).** `GetLegacySigOpCount`/`GetP2SHSigOpCount` (the `MAX_BLOCK_SIGOPS` check in `ConnectBlock`) count only `CHECKSIG`/`CHECKMULTISIG`; the 20-per-opcode `GetPQSigOpCount` (`src/policy/policy.cpp:403-440`) is policy, used in ATMP (`main.cpp:1832`) and the miner (`miner.cpp:567`). `OP_CHECKSETSIG` verifies up to `k ≤ 15` recoverable signatures, **never cached** (`checker.cpp:42` → `SetSnapshot::CheckSetSigs`, `state.cpp:289-307`; plan §15.2: "Set-signature checks are not cached"). A valid 2 MB block can carry ≈ 1,500-2,000 15-signature vault spends → 22,000-30,000 recoveries ≈ 0.9-1.2 s at the verifier's measured 39 µs (spread over the script-check threads), beyond the 20,000-sigop ECDSA ceiling (which is cached on relay); or ≈ 250 SLH-DSA-SHA2-128s / ≈ 3,000 Falcon-512 verifications (well under a second at published costs). The plan already states the choice for `OP_CHECKSETSIG` (§15.2 rule 6, line 835: "It does not add to the legacy sigop count (counting it would reprice historical blocks); its cost is bounded by `seats ≤ 15` and rule 6") but without numbers, and the quantum spec's F-5 (`yellowback-quantum-spec.md:7`) makes the same choice for `OP_CHECKPQSIG`, likewise without a measured per-block worst case; there is no CI measurement. Both lines identical.

## 2. Root cause

- `src/vault/state.cpp:370-379` — atomicity of `ApplyTx` implemented as copy-on-apply of the whole overlay.
- `src/script/script.cpp` `GetSigOpCount` unchanged by design; no per-block budget for the new opcodes; no benchmark guarding the worst case.

## 3. Fix options considered

- **A. Journal instead of copy (W3-V-4; recommended).** Apply `ApplyTxInner` directly to `changes`, recording for each key's *first* write in the transaction its previous overlay state (absent / present-with-value / present-erased); on failure roll back from the journal. Per-transaction cost becomes proportional to the keys it touches; `ApplyTx` stays atomic. Behaviour-preserving; lives in a gated file (rule 7 allows it only with a finding and an equivalence argument — this is both).
- **B. Accept the opcode costs explicitly, with numbers and a CI benchmark (W3-V-6/N-1; recommended now).** Bounded by block size, by one `OP_CHECKSETSIG` and one `OP_CHECKPQSIG` per script evaluation, and by `k ≤ 15`; comparable to stock's worst case; parallelised over script threads. Record it in the plan and measure it nightly so a regression (or a parameter change such as more seats) is seen.
- **C. A Vault-gated consensus per-block budget** (count `k` per executed `OP_CHECKSETSIG` input and 20 per `OP_CHECKPQSIG` input against a new `MAX_BLOCK_VAULT_SIGOPS`, evaluated in `ConnectBlock` only for vault-active blocks so historical blocks are not repriced). Real bound, but a new consensus rule with its own counting path (the opcodes sit in scriptSigs/P2SH redeem scripts, so counting is per input after script parsing), vectors and miner support. Owner decision **before P8**; not recommended unless the bench in B exceeds the budget below.
- **D. Cache set signatures.** Rejected: the plan forbids it for a reason (membership is state-dependent at the spend height; a cache entry would need the snapshot generation in its key).

## 4. Recommended fix

1. **Journal (both lines, `src/vault/state.{h,cpp}`):**
   - add to `VaultState` a private `std::vector<std::pair<std::string, std::optional<std::optional<std::string>>>>* journal = nullptr;` (outer optional = "key was absent from `changes`");
   - in `Put`/`Erase` (`state.h:409-410`; `PutRecord` goes through `Put`): `if (journal && !journaled.count(key)) { auto it = changes.find(key); journal->emplace_back(key, it == changes.end() ? std::nullopt : std::optional<std::optional<std::string>>(it->second)); journaled.insert(key); }` before the write (a per-transaction `std::set<std::string> journaled`);
   - `ApplyTx` (`:370-379`): set `journal`, run `ApplyTxInner(tx, height, coins)` on `*this`; on error replay the journal in reverse (absent → `changes.erase(key)`, else restore the value), clear it and return the error; on success clear it. Remove the child copy and `MergeFrom`'s use here (keep `MergeFrom` if other callers use it — grep).
   - `blockHashes` / `activationHeight` were copied into the child (`:373-374`); they are already members of `*this` — nothing to copy.
   - **Rule 7:** no other edits in `state.cpp`; the PR states the equivalence ("the overlay after `ApplyTx` — success or failure — is byte-identical to the copy-on-apply implementation for every input") and the tests below prove it.
2. **Decision and numbers (workspace docs).** Plan §15.2 rule 6: add "Worst case measured (2026-10-13, 39 µs per recovery, one core): ≈ 30,000 recoveries ≈ 1.2 s per 2 MB block, parallel across script threads; accepted (W3-V-6/N-1), guarded by the nightly bench"; the quantum spec's F-5 note (the ≈ 250 SLH-DSA-128s / ≈ 3,000 Falcon-512 verifications per block) and the `doc/yellowback-pq-dos.md` "gated by" paragraph are written once by `LOW-W3-PQ-3-ycash-pq-verify-cost-ci-gate.md` §4 step 4 — supply the numbers there, do not edit F-5 here; `doc/yellowback-pq-dos.md`: this report's own "per-block (valid block) cost" section next to the mempool numbers; `docs/mapping.md` §22 row ("no consensus sigop cost for the vault opcodes: why; the bench"). If the owner prefers option C, record that instead and open the consensus PR before P8.
3. **Benchmark (both lines).** `src/bench/vault_block_bench.cpp` (the tree's bench framework): (i) a synthetic block of N 15-signature vault spends validated through `CScriptCheck` with a real `SetSnapshot`; (ii) a block of `T` state-changing transactions through `VaultState::ApplyBlock` (before/after the journal); (iii) N SLH-DSA-128s and Falcon-512 owner spends. A nightly, report-only workflow step prints the timings and fails only above a generous budget (e.g. > 3 s for (i) or (iii), > 0.5 s for (ii) at T = 8,000 on the CI runner) — calibrate on the first runs and write the budget into `doc/yellowback-pq-dos.md`.

## 5. Tests

- **Unit `src/test/vault_state_tests.cpp`:** the existing `apply_tx_is_atomic` and every `ApplyBlock` test pass unchanged; add a case where a transaction writes a key already in the overlay and then fails (rollback must restore the earlier overlay value, not erase it) and one where it erases a key and fails (rollback restores presence).
- **Differential fuzz (`vault_state_fuzz_harness.h`, `vault_fuzz_tests.cpp`):** feed the same random transaction sequences to a reference copy-on-apply `VaultState` (kept in the test harness only) and to the journaled one; assert identical `changes`, identical `MakeUndo()` and identical verdicts — this is the test that makes the gated change reviewable.
- **Performance assertion (unit, coarse):** `ApplyBlock` of 8,000 synthetic heartbeats over distinct sets completes in < 1 s in a Release build (skipped under sanitizers) — would have caught W3-V-4.
- **Bench:** as above; the nightly step's output in the run log.
- **Cross-line:** vault vectors, golden and replay-parity tests unchanged on both lines (no rule change).

## 6. Acceptance criteria

- `ApplyTx` no longer copies the overlay; per-transaction cost is proportional to the keys the transaction touches; the differential fuzz and all existing vault tests pass on both lines; two independent reviewers (gated file) with the equivalence statement in the PR.
- The plan, the quantum spec and `doc/yellowback-pq-dos.md` record the per-block worst case and the decision (accepted with bench, or cap chosen); the nightly bench runs on both lines.

## 7. Risks and side effects

- **Journal bug = consensus bug.** A rollback that leaves a stray key changes the state hash and splits nodes. Mitigated by the differential fuzz, the state-hash comparisons in `vault_undo_prune.py`, and the review gate. Land before P8.
- **Option C, if chosen:** a new block-validity rule; vectors, miner and pool (yolo) template limits must follow.

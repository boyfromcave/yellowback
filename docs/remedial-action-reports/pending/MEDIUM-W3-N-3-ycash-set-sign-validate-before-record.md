## 1. Finding

`set_signunlock` (`ycash-dd/src/rpc/vault.cpp:1797-1830`) is `DecodeMutable` → `FindTemplateInput` (coin unspent, kind) → `SignSetInPlace`; `set_signcancel` (`:1938-1958`) the same with role 2. `SignSetInPlace` (`:1640-1720`) computes the ACP sighash, refuses a different recorded `(role, sighash)` (`:1670-1675`), then — for the first member key it holds — writes the record `WriteVaultSetSig(setId, prevout, role, sighash)` (`:1692`) and signs (`SignRecoverable`, `:1697`). Record-before-sign is correct. What is missing is **validate-before-record**: no `vault::CheckTx` (S-2 value / covenant, S-3, I-0, I-2 cancel deadline and "back to the vault" output, the module's `ValidateSpend`), no check that the outputs re-lock or pay intents, no check that existing signatures on the hex are current members. Consensus `ACT_SET_EQUIVOCATION` (`src/vault/state.cpp:845-870`) needs only two recoverable signatures by one current member over different `(role, sighash)` for one `(setId, prevout)`; it does not ask whether either transaction was valid or unspent.

Griefing path (verifier, exact): a builder — or a buggy client — hands member M an unlock of vault V whose intents exceed V's value (`bad-txns-vault-value`) or whose outputs otherwise break S-2. M's wallet records `(setId, V) → (UNLOCK, sighash_bad)` and signs a transaction that can never confirm. Every later correct build of V has a different sighash, so M's node refuses it forever (`set-sign-once`, "There is no override", `doc/vault-rpc.md:335`); there is no RPC that removes a record (`set_importsigned` refuses conflicts `:2043-2079`, `set_acknowledgerestore` only clears the restore marker `:2081-2103`, "There is no RPC that deletes a record" `doc/vault-rpc.md:451-452`); and signing anyway from a key copy is a provable equivocation (ejection + frozen bond). If `unlockthreshold` current members are each handed the same bad hex, V cannot be unlocked by the set until `ownerHeight`. Role 2 (cancel) is a separate record, so cancels of V's intents are unaffected; a bad cancel hex poisons that intent's cancel for its signers in the same way. W3-N-14(b): `have` is built from `RecoverSig` over the signatures already on the hex (`:1655-1660`) with no `IsCurrent` filter, and `complete` is `sigs.size() == k` (`:1707`), so a hex carrying a stray non-member signature reports `complete: true` and then fails relay with `SCRIPT_ERR_SETSIG`. Identical on `ycash6` (`SignSetInPlace` `:1661-1741`, record `:1713`, sign `:1718`, `set_signunlock` `:1818`, `set_signcancel` `:1959`).

## 2. Root cause

- `src/rpc/vault.cpp:1640-1720` — the only checks before `WriteVaultSetSig` (`:1692`) are: the set exists and has a threshold for the role (`:1644-1646`), the selector on an already-signed scriptSig matches the role (`:1651-1654`), existing signatures recover (`:1655-1660`), and the record does not conflict (`:1666-1679`).
- `src/rpc/vault.cpp:1655-1660`, `:1707` — existing signatures are counted, not membership-checked (N-14(b)).
- No read-only path shows an operator what a signature would bind (decoded outputs, sighash, record status, validity) before the irreversible step.

## 3. Fix options considered

1. **Validate before the record is written (recommended).** Run the primitive's own rules on the hex at the next height (the same `vault::CheckTx` ATMP and the miner use) on a probe copy, plus the structural checks; refuse with a precise error and write nothing. A member then never records a sighash that cannot confirm for reasons visible at its tip.
2. **A record-delete RPC** (`set_forgetsigned {setid, prevout}`), gated on "the prevout is unspent and no transaction carrying the recorded sighash is in the chain or mempool" (the auditor's suggestion). **Rejected — must not be added.** Equivocation is a property of two signatures, not of transactions: once the wallet has *returned* a signature over `sighash_bad` (in `set_signunlock`'s result, which the caller can store, forward, or embed in a never-broadcast hex), deleting the record cannot recall it. The gate checks only the chain and the mempool, and the dangerous case is exactly the signed-but-never-broadcast hex the builder keeps (the same blind spot 07/F-5 option 4 and 05/N-1 describe): the builder waits until the member signs the correct build after a "forget", then submits `set_equivocation` with both signatures → M is EJECTED and its bond frozen. Any delete turns a recoverable liveness loss (wait for `ownerHeight` or let other members sign) into an unrecoverable slashing. The only safe "undo" would be consensus-level (an equivocation exemption for provably invalid transactions), which the primitive deliberately does not have.
3. **Full template-script dry-run with the prospective signatures.** `OP_CHECKSETSIG` pops exactly `k` signatures, so a partially signed input cannot be script-verified until complete. The structural checks of (1) cover what a partial dry-run could; the full isolated script check runs only for the signature that completes the set (step 5 below).

## 4. Recommended fix

1. **Validation helper** `ValidateSetSpend(const CMutableTransaction& mtx, size_t idx, uint8_t role, std::string& reason, std::vector<std::string>& warnings)` in `src/rpc/vault.cpp`, called by `SignSetInPlace` **before** `ReadVaultSetSig` and before any key is touched:
   - **Probe.** Copy `mtx`; if `vin[idx].scriptSig` is empty, set it to the selector only (`CScript() << (role == ROLE_UNLOCK ? OP_1 : OP_2)`), because `ApplyTxInner` refuses an empty scriptSig with `bad-txns-vault-selector` (`state.cpp:479-480`, `ParseSelector` needs a final `OP_1..OP_4`, `template.cpp:316-336`); existing signatures stay (they are not read by the state rules).
   - **Coins.** `CCoinsViewMemPool viewMempool(pcoinsTip, mempool); CCoinsViewCache view(&viewMempool);` then `vault::ViewCoinAccessor coins(view, NextHeight())` (`vault/node.cpp:68-76`), under `LOCK2(cs_main, mempool.cs)` (the RPC already holds `cs_main`).
   - **Rules.** `vault::CheckTx(probe, coins, NextHeight(), *vault::TipSnapshot(), vault::AncestorHashes(chainActive.Tip()), activationHeight)` (`state.cpp:886-893`) — exactly ATMP's call (`main.cpp:1805-1813`). If it fails only with `bad-txns-vault-inputs-missing` (`state.cpp:465`) for a **non-template** input (a fee input already spent — the case `vault_refee` exists for), re-run on a probe whose `vin` is the template input alone: the fee inputs are not under the set signature (ACP), so the build is still signable and the reason is returned as a warning ("re-fund with vault_refee before sending").
   - **Transient vs permanent.** `bad-txns-vault-rate` (S-3, `state.cpp:527`) depends on the epoch and on pending unlocks; return it as a warning and sign. Every other failure — `bad-txns-vault-value`, `-covenant`, `-amount`, `-intent`, `-selector`, `-multi`, `-app`, `-malformed`, `-noset`, `-release`, `-cancel` (I-2's deadline or missing "back to vault" output, `state.cpp:545`, `:550`), `-preactivation`, and module reasons (`bad-yellowback-*`, e.g. `bad-yellowback-vault-unlock` for any set-unlock of a YED vault, `yellowback/module.cpp:83`) — refuses: `set-sign-invalid: <reason>; nothing was recorded or signed`.
   - **Structural.** The template input is the one `FindTemplateInput` found (S-1); for role 1 the template is a V and `setId == vp.setId`; for role 2 an I and `setId == ip.cancelSetId`; `nExpiryHeight == 0` (builds are made with no expiry, `NewTx` `:717-722`; a signed build that can expire would need a second signature — refuse a non-zero expiry); `SetSighash` uses `NextBranchId()` (unchanged; see `LOW-W3-N-5`).
2. **Existing signatures (N-14(b)).** In `SignSetInPlace` replace the `have` loop (`:1655-1660`) with: each recovered key must be a current member (`IsCurrent(*s, member, h)`, as `SetSnapshot::CheckSetSigs` does, `state.cpp:289-307`) and distinct; otherwise refuse `set-sign-invalid: signature <i> is not by a current member of <setid>` before anything is recorded. `complete` then means "k valid current-member signatures".
3. **Order in `SignSetInPlace`.** Validate (step 1) → existing signatures (step 2) → the record check and restore-marker logic exactly as today (`:1666-1691`) → write the record → sign. The validation adds no path that writes or signs; the record-before-sign invariant is untouched.
4. **Completing signature.** When the signatures reach `k`, run the isolated template-input script check as ATMP does (`CScriptCheck` with `STANDARD_SCRIPT_VERIFY_FLAGS | GetVaultScriptFlags(NextHeight())`, `SetVault(snapshot, NextHeight())`, `main.cpp:1935-1954`) on the result and report `complete: true` only if it passes; otherwise `complete: false` with `"scripterror"`. (The signature is already recorded and returned — this is a report, not a guard.)
5. **Inspect path (write-nothing).** New RPC `set_checksign "hex"` (wallet, read-only): returns `{"kind", "setid", "role", "prevout", "sighash", "required", "signatures": [{"key", "current"}], "record": "none" | "same" | "conflict", "recorded": {"role","sighash"} | null, "restored": bool, "valid": bool, "reason": string | null, "warnings": [...], "outputs": [{"n","amount","kind","address"|"script"}], "wouldsign": [memberkey]}`. It performs steps 1-2 and reads the record, and never writes or signs. Document it as **the** step before `set_signunlock`/`set_signcancel` for any hex that came from another node.
6. **No delete.** Keep `doc/vault-rpc.md:451-452` ("There is no RPC that deletes a record") and add the reason from §3 option 2 in one paragraph: a deleted record does not delete the signature; the builder holding it can slash you after you sign again; the recovery from a poisoned prevout is waiting for `ownerHeight` (UNLOCK) or the intent's `delay` (CANCEL lapses into RELEASE), or other members who did not sign the bad build.
7. **Docs** — `doc/vault-rpc.md` `set_signunlock` (`:320-366`): "validates the spend first (the vault rules at the next block: `vault::CheckTx`); a spend that cannot confirm is refused (`set-sign-invalid`) and nothing is recorded; a rate-limited unlock is signed with a warning"; new `set_checksign` section; error table rows `set-sign-invalid`. Contract JSON for `set_checksign` and the new `scripterror`/`warnings` fields of `SetSigResult` (additive). Both lines.

## 5. Tests

- **Functional `qa/rpc-tests/vault_rpc.py` (both lines) — the regression that would have caught it:** a hand-built unlock of V whose intents sum above V's value → `set_signunlock` refuses `set-sign-invalid: bad-txns-vault-value`, `set_listsigned` unchanged; then the correct build signs normally (no `set-sign-once`). Same for a cancel whose "back to the vault" output is short (`bad-txns-vault-cancel`), a cancel after the intent's `delay` (deadline), a YED vault set-unlock (`bad-yellowback-vault-unlock`, in `yellowback_claim.py` or `vault_bridge.py` where YED is configured).
- **Rate-limit warning:** an unlock over the epoch's cap signs with `warnings: ["bad-txns-vault-rate"]` and confirms in the next epoch.
- **Spent fee input:** a signed build whose fee coin was spent: `set_signunlock` by the next member signs with the re-fund warning; `vault_refee` + `vault_send` confirm (extends `vault_refee.py:184-198`; ycash6 `:189-203`).
- **N-14(b):** a hex carrying one signature by a non-member key (signed with `sign_recoverable` in the test framework) → `set-sign-invalid`; a hex carrying `k` valid signatures → `complete: true`; a hex whose last signature makes `k` but whose script fails (e.g. a member that was ejected between signatures) → `complete: false` with `scripterror`.
- **`set_checksign`:** shape in `vault_rpc_contract.py`; `record: "conflict"` after signing a different build; never changes `set_listsigned`.
- **Hawkeye:** its mock (`mock.rs`) returns `set-sign-invalid` for an invalid build so the engine's error path is exercised in `cargo test --locked`.

## 6. Acceptance criteria

- No sign-once record is written for a build that `vault::CheckTx` refuses at the next height for a non-transient reason; the refusal names the reason and `set_listsigned` is unchanged.
- `complete: true` implies `k` current-member signatures and a passing template script check at the next height.
- `set_checksign` exists, writes nothing, and is in the contract; the doc explains why there is no delete.
- Both node lines; Hawkeye and YecWallet flows unchanged for valid builds.

## 7. Risks and side effects

- **No consensus effect.** The wallet refuses more, never signs more.
- **Tip-dependence:** validation is at the signer's tip; a build valid at the builder's tip but not at a lagging signer's (a mempool parent not yet seen) fails with `bad-txns-vault-inputs-missing` for the template input → refused; the member retries after syncing. Correct direction.
- **Module rules may be price/attestation-dependent** (YED). Treat any `bad-yellowback-*` reason that the module documents as tip-transient like the rate limit (warning) only after the module owner lists them; until then refuse (a refusal is recoverable, a wasted signature is not).
- **Cost:** one `CheckTx` per sign call (≤ 16 recoveries for an act-carrying hex after `MEDIUM-W3-N-4`; set spends carry none) — negligible.

## 1. Finding

**W3-N-2 — no cap, self-send first.** `vault_refee "hex"` is documented as "**Anyone may re-fund**" (`doc/vault-rpc.md:409`) and is the member's remedy when a signed spend lingers or is pinned (`:423-428`). `Refee` (`ycash-dd/src/rpc/vault.cpp:891-943`) drops every non-template input and computes `needed = Σ outputs + VAULT_RPC_FEE − coin.nValue` (`:905-907`) with no upper bound. Every output is set-signed, so a builder may have included an arbitrary change output to itself; a member who re-funds that build pays the builder's change. `ExactCoin(needed, …)` (`:866-885`) either picks an existing coin within `VAULT_RPC_MIN_CHANGE` above `needed` or **builds, signs and broadcasts a self-send of exactly `needed`** (`:878-884`) before `Refee` has checked anything; if anything after it throws (the `SetSighash` mismatch `:915-916`, the two new refusals `:924-928` / `:932-937`, `RememberBuild`'s DB write `:854-855`) the split stays in the mempool (its output locked, not lost, but unrequested) while the refusal text says "nothing was changed". The result's `fee` (`:1991-1996`, `:2001`) is computed after the fact; nothing is shown before. The refee-utxo delta added a post-hoc check `fee = in − out ∈ (0, YedMaxTxFee()]` (`:917-937`); on every path that adds an input that fee is `VAULT_RPC_FEE` plus an excess below `VAULT_RPC_MIN_CHANGE` — 10,000-10,999 zatoshi by construction — so it never sees the amount paid to set-signed outputs (W4-N-3, below).

The wave-3 verifier downgraded it to Low: on its own the call costs the operator `VAULT_RPC_FEE` for the split and one locked coin of `needed`, bounded by the wallet's confirmed transparent balance (`Fund` throws at `:781-782`); the value leaves the wallet only when `vault_send` signs the re-funded spend — i.e. W3-N-1. Its weight is as N-1's amplifier: a builder's large "change" is paid by whoever re-funds and sends. Hawkeye calls `vault_refee` only on its own stored hex and then checks that only the fee inputs changed (`same_set_signed_spend`, `sign.rs:505-518`).

**W4-N-2 (Low) — a foreign hex unlocks, and may spend, the operator's locked coins.** `Refee` builds `old` from **every** non-template input of the caller's hex (`:894-896`) and unlocks each one this wallet has locked (`:900-903`), whatever locked it: an operator's `lockunspent`, or another remembered build's fee input. On success every `old` coin not in the new input set is unlocked again (`:938-941`), so the protection is gone for good. The split's `Fund(split, 0)` (`:880`) chooses from `EligibleCoins(used = {})` — `ExactCoin`'s `exclude`/`replacing` reach only the exact-coin search (`:868-870`) — and the delta's comment states this as intended ("which may spend a still-unspent replaced input", `:862-864`). Scenario: a counterparty hands the operator a "please re-fund" hex whose template input is any unspent vault (public) and whose fee input is one of the operator's outpoints (public on the transparent chain) — a coin it protected with `lockunspent`, or the fee coin of a build its members are signing. `vault_refee` unlocks it; with no exact coin the split self-sends from the largest eligible coins, which may now include it. Value stays in the wallet unless `vault_send` follows (W3-N-1), but the protected coin is consumed, and another build loses its fee input and needs a re-fund. Predates the delta (01/V-2's `Refee`); refee-utxo re-reasoned and kept it.

**W4-N-3 (Info) — the "(0, cap]" check is defence in depth, not a bound.** `fee <= 0` cannot occur (an exact coin is ≥ `needed`; a split output is exactly `needed`; with `needed <= 0` no input is added and `fee ≥ VAULT_RPC_FEE`). `fee > YedMaxTxFee()` needs either outputs short of the template coin by more than the cap (consensus-invalid for an UNLOCK, `bad-txns-vault-value`, `src/vault/state.cpp:523`) or a cap at its floor (`-maxtxfee=0.0001` without an attested price, `src/init.cpp:1445`, `src/policy/policy.cpp:490-499`) together with an exact coin carrying excess — then `ExactCoin`, smallest fitting coin first, keeps choosing it and every re-fund is refused. The pre-existing `SetSighash` mismatch throw (`:915-916`) neither releases the new coin nor re-locks `released`, unlike the two new refusals (`:925-926`, `:933-934`).

**W4-N-4 (Info) — the two new refusals are undocumented.** `vault_refee`'s help (`:1963-1974`) mentions neither the fee bound nor the replaced-input exclusion; nor do `doc/vault-rpc.md`'s error table (`:515+`) and `doc/vault-rpc-contract.json` (`errors`; only its `source.sha256` moved). Both refusals are `RPC_WALLET_ERROR` (-4) with free text, and the same "vault_refee: …" text is raised from `vault_buildunlock`'s and `BuildIntentCancel`'s re-fund paths (`:1780`, `:1887`), naming an RPC the caller did not call.

Identical on `ycash6` (the delta is the same on both lines): `Fund` `:775-807`, `ExactCoin` `:883-902` (split `:895-901`), `Refee` `:908-960` (release `:917-920`, `needed` `:924`, sighash check `:932-933`, refusals `:941-945` / `:949-954`, final unlock `:955-958`), `vault_refee` `:1981-2027` (help `:1984-1995`), re-fund calls `:1801`, `:1908`.

## 2. Root cause

- `src/rpc/vault.cpp:905-907` (ycash6 `:922-924`) — `needed` is unbounded; nothing distinguishes "the fee" from "a third party's change".
- `src/rpc/vault.cpp:878-884` (ycash6 `:895-901`) — `ExactCoin` broadcasts the split inside the re-fund, before any check; `:915-937` check afterwards.
- `src/rpc/vault.cpp:900-903`, `:938-941` (ycash6 `:917-920`, `:955-958`) — the release covers every locked input of the caller's hex, not this wallet's own build's fee inputs; `:880` (ycash6 `:897`) — the split excludes nothing.
- `src/rpc/vault.cpp:1960-2006` (ycash6 `:1981-2027`) — no option to bound or preview the funding; help text and error strings not updated.

## 3. Fix options considered

1. **Cap the wallet's net funding before anything moves; explicit `maxfund` override (recommended).** `netfund = needed − Σ(outputs paying this wallet's own scripts)`; refuse when `netfund > VAULT_RPC_FEE + VAULT_RPC_MIN_CHANGE` unless the caller passes `{"maxfund": amount}` ≥ `netfund`. For this wallet's own remembered build the change output is the wallet's, so `netfund` is just the fee and nothing changes for Hawkeye or the builder; a re-fund of a foreign build with a large change output must be acknowledged with an amount.
2. **Rely on refee-utxo's "(0, cap]" fee check.** Rejected (wave 4, W4-N-3): it bounds `in − out`, which is fixed at 10,000-10,999 zatoshi on every reachable path, never the value paid to set-signed outputs, and it runs after the split broadcast.
3. **Refuse to re-fund any hex that is not this wallet's remembered build.** Breaks the documented "anyone may re-fund" remedy against pinning (`doc/vault-rpc.md:423-428`) and against a builder that spent its own fee coin (the MEDIUM-01-V-2 use case). Rejected.
4. **Multi-input exact funding instead of a self-send.** The set signatures bind the outputs, not the number of inputs, so several existing coins summing to `needed` (within `VAULT_RPC_MIN_CHANGE`; the excess becomes fee) avoid the split. Worth doing as a preference, not as the fix.
5. **W4-N-2: keep releasing every locked input but exclude them from the split.** Leaves the `lockunspent` protection removed on success (`:938-941`). Rejected in favour of releasing only this wallet's own build's fee inputs.

## 4. Recommended fix

1. **Order (W3-N-2; wave-4 correction (a)).** In `Refee` (`:891-943`): compute `needed` and `netfund` and apply the cap (step 2) **before** the lock release (`:900-903`) and before any coin selection (`:909-910`) — not alongside the post-hoc check at `:917-937`. Move the `SetSighash` invariant (`:915-916`) to a dry computation on a copy whose fee input is a placeholder (the ACP digest does not depend on fee inputs), also before any side effect; this also removes W4-N-3's un-unwound throw.
2. **Cap.** `vault_refee "hex" ( {"maxfund": amount, "dryrun": bool} )`. Refuse with `RPC_WALLET_ERROR` `vault-refee-over-cap: re-funding needs <needed> (<netfund> beyond outputs to this wallet, of which <fee> is the fee); pass maxfund to accept` when `netfund > VAULT_RPC_FEE + VAULT_RPC_MIN_CHANGE` and `maxfund` is absent or smaller. The internal re-fund paths of `vault_buildunlock` (`:1779-1781`) and `BuildIntentCancel` (`:1886-1888`) re-fund this wallet's own memo, whose change output is its own, so they pass without an option.
3. **Release only this wallet's own build's fee inputs (W4-N-2).** `released = old ∩ feeInputs(mapVaultBuilds[templ])` (the remembered build for the same template outpoint; `UnlockBuildInputs` semantics); every other locked coin in `old` stays locked. Replace the final unlock (`:938-941`) by "unlock the `released` coins not in the new input set". When `vault_refee` replaces the memo (`:1990`, `RememberBuild` on equal outputs), unlock the old memo's fee inputs that are not in the new transaction (today they stay locked in memory until restart). Give `Fund` an `exclude` parameter and pass `exclude = {templ} ∪ (old \ released)` to the split's `Fund`, so a foreign hex's inputs are never spent by the split; the memo's own released fee inputs may still fund it (the intended "a still-unspent one can fund it", `doc/vault-rpc.md:414-415`).
4. **Pick, check, then broadcast (W3-N-2 "build the split last").** Split `ExactCoin` (`:866-885`) into a side-effect-free `PickExactCoin(value, exclude, replacing)` → `{exact coin | none}` and `BroadcastSplit(value, exclude)`. `Refee` picks; if no exact coin, the new input's value is `needed` by construction. Run every check on that candidate (cap, sighash invariant, fee in `(0, cap]`, the new input unspent — via the helper of `LOW-W4-N-1` — and not a replaced input); only then lock the exact coin or broadcast the split. A refusal then really changes nothing.
5. **Exact multi-coin funding before the split (option 4; wave-4 correction (b)).** In `PickExactCoin`, after the single-coin search, try the smallest set of up to 3 coins whose sum is in `[value, value + VAULT_RPC_MIN_CHANGE)`, **excluding `replacing`** exactly as the single-coin search does since refee-utxo (`:868-870`) and excluding `old \ released`. Return whether a split was broadcast; `vault_refee` reports `"split": txid | null` (wave-4 correction (c): this is what makes "nothing was changed" checkable).
6. **Keep the "(0, cap]" check (W4-N-3)** as defence in depth after the reorder; do not count it as the W3-N-2 bound.
7. **Dryrun.** `{"dryrun": true}` returns `{needed, netfund, fee, wouldsplit, sighash, release: [outpoint], keeplocked: [outpoint]}` without locking, unlocking, splitting or writing anything.
8. **Registry.** The coin(s) chosen are recorded in `MEDIUM-W3-N-1`'s `vaultfeein` registry against the hex's outputs digest only after every check passed; a refused re-fund records nothing.
9. **Errors (W4-N-4).** Stable reason prefixes for the refusals: `vault-refee-over-cap` (step 2), `vault-refee-input` (today's "is spent or is a replaced input", `:927`), `vault-refee-fee` (today's fee refusal, `:935`); the message names the operation ("re-funding: …"), not `vault_refee`, since `vault_buildunlock`/`vault_buildcancel` raise them too.
10. **Docs (both lines).** `vault_refee` help (`:1963-1974`) and `doc/vault-rpc.md` `vault_refee` (`:400-428`): the cap, `maxfund`, `dryrun`, `split`; "only this wallet's own remembered build's fee inputs are released; other locked coins named in the hex stay locked"; "re-funding a build someone else made pays its outputs: check them (`dryrun`) before `maxfund`". Error table (`:515+`): rows for `vault-refee-over-cap`, `vault-refee-input`, `vault-refee-fee`, raised by `vault_refee`, `vault_buildunlock`, `vault_buildcancel`. `doc/vault-rpc-contract.json`: the options object, `split`, the dryrun shape, the three `errors` entries (and the regenerated `source.sha256`).

## 5. Tests

- **Functional `qa/rpc-tests/vault_refee.py` (both lines) — would have caught W3-N-2:** node 1 builds an unlock with an extra 5-YEC change output to itself (signed by the set); node 0 `vault_refee` → `vault-refee-over-cap` naming `needed`/`netfund`; node 0's mempool has **no** new transaction (no split was broadcast) and `listlockunspent` is unchanged; with `{"maxfund": 5.0002}` the re-fund succeeds and reports `split`; `dryrun` reports the same numbers and leaves the mempool and the locked-coin list unchanged.
- **W4-N-2:** node 0 `lockunspent false` on one of its coins C; node 1 hands it a hex (any unspent vault as template input, C as fee input); `n0.vault_refee(hex)` → C is still in `listlockunspent`, is not spent by any split (check the split's inputs, and `gettxout(C)`); a second case where C is the fee input of node 0's own remembered build of another vault → that build's `vault_buildunlock` still returns `reused`, not `refunded`.
- **Refusal branches (W4-N-3/N-4):** the fee-refusal case (`-maxtxfee=0.0001`, no attested price, only an exact coin with excess → `vault-refee-fee`, no split, locks restored) is owned by `LOW-W4-N-5-ycash-refee-utxo-test-fidelity.md` §4 item 4(ii), which asserts this report's stable reason once both land; the input refusal (a fee input spent between pick and check, `vault-refee-input`) by `LOW-W4-N-1-ycash-mempool-spent-fee-coins.md` §5. This report owns `vault_rpc_contract.py` provoking each new `errors` entry.
- **Unchanged behaviour:** the existing re-fund of the wallet's own build after its fee coin was spent (`vault_refee.py:184-198`; ycash6 `:189-203`) and of a cancel (`:216`; ycash6 `:221`) succeed without options; the refee-utxo rounds (`:227-266`) pass.
- **Unit-level (optional):** the multi-coin exact search on a synthetic coin list, with `replacing` excluded.

## 6. Acceptance criteria

- `vault_refee` never funds more than the fee plus `VAULT_RPC_MIN_CHANGE` beyond the outputs paying this wallet unless `maxfund` says so; it broadcasts, locks and unlocks nothing when it refuses; `split` and `dryrun` are in the contract.
- A coin this wallet locked for any reason other than its own remembered build of the same template outpoint stays locked across `vault_refee` and is never spent by its split.
- Each refusal has a stable reason in the help text, `doc/vault-rpc.md`'s error table and `doc/vault-rpc-contract.json`, provoked by `vault_rpc_contract.py`.
- Hawkeye's refee path and the builder's own re-fund paths pass without options on both lines.

## 7. Risks and side effects

- No consensus effect. A member re-funding a foreign build with a large change must now state an amount — intended. Pinning remedies keep working: a pinned variant has the same outputs, so `netfund` is the same as the original funder's.
- W4-N-2's narrower release: a re-fund of a foreign hex whose fee input happens to be this wallet's only coin no longer self-funds from it (the coin stays locked); the operator unlocks it explicitly if that was intended.
- Error strings change from free text to prefixed reasons; check Hawkeye's error mapping and its mock (`crates/hawkeye-ycash/src/mock.rs`).

## 1. Finding

yb-calibration exists to derive and check the constants a Yellowback release locks into the node. Its model layer (vendored reference, golden vector, kernels) was moved to the upgrade line on 2026-10-13 (D-MP-1, pin ycash6 `1310a41a1`, consensus-equivalent to `0742e43`), but everything that produces a recommendation — the parameter registry, the simulator, studies G1–G9, the policy base set, the `params.cpp` patch emitter and the lock-readiness checklist — still runs on the retired v3 set at ycash6 `7702d22`. Against the node being released: **26 node fields have no registry entry** (23 calibration fields — `claimDelay`, `feeBands[0..2]`, `feeFloorCents`, `earlyRedeemFeeBps[0..2]`, `maxVaultShareBps`, `vaultShareFloorCents`, `issuedBeforeStart`, `residualMinCents`, `bondMinFloorZat`, `bondMinCapZat`, `bondShareBps`, `seatAgeUnit`, `seatAgeCap`, `seatMarginBps`, `evictMarginBps`, `attestorSeats`, `attestorCancelThreshold`, `attestorUnlockThreshold`, `attestorLivenessMin` — plus the identity fields `pqAddressVersion`, `attestorSetId`, `pqFalconHeight`); **12 registry entries no longer exist in the node** (`abandonBlocks`, `activationDelay`, `activationThreshold`, `bondMin`, `enforceUntilHeight`, `enforcementFloor`, `enforcementResume`, `feeBps`, `feeMin`, `participationFloor`, `signalWindow`, `valveBlocks`); **15 values differ**, including the class A/C base ratios, which are inverted (registry `baseRatioBps[0]` 50,000 / `[2]` 30,000 vs node 30,000 / 50,000), `claimThresholdBps` 11,000 vs 12,500 and `maxMint` $10,000 vs $100,000. The policy's headline tolerance, "P(collateral < debt when the claim path opens)", is also a v3 notion that in-term claims (IT-2) make moot.

Nothing stops an operator from treating the output as a release input. `ybcal params check` (CI) compares the registry with its own `7702d22` snapshot and passes; pointed at the release line (`--ref HEAD`) it fails closed and cannot read it. The lock-readiness checklist has no "registry pin = release line" item, its "every locked parameter has a recommendation" check iterates the registry and so passes vacuously for the 26 missing fields, and the patch check is advisory and runs at `7702d22`. A `recommend` run (verification `:58-65`) writes `recommended.json` with `base_commit` `7702d22…`, θ 11,000, `baseRatioBps[0]` 50,000, `maxMint` 1,000,000 and the withdrawn heights 3,075,000 / 3,495,480; the report says "1 value(s) move off the shipped set" and the patch file says "the recommended set equals the shipped SetCommon()/MainParams() values" — false against the node being released (W4 03/new-2). No line of `report.md` or `recommended.json` says "retired"; only module docstrings, `README.md:75-85` and D-MP-1 do, and the real-data report's lock-readiness §7 lists calendar and owner items but not the re-pin. **Failure scenario:** at P8 a reviewer cites a green CI, a passing `params check` and a `lock-ready: yes` real-data report as calibration evidence for the upgrade-line constants; the evidence is about a parameter set the node no longer has. (Mitigations that keep this at Medium: no mainnet `UPGRADE_VAULT` height exists; every current upgrade-line value is an owner decision behind the two-person consensus gate; the emitted patch's hunks carry `7702d22` context and would fail `git apply` at HEAD. It becomes High if the P8 gate cites ybcal lock-readiness before the re-pin.)

## 4. Recommended fix

**Part 1 — guard and stamp (branch `fix/W4-K-1-registry-pin-guard`, lands first; no change to any study's numbers):**

1. `src/ybcal/params/registry.py`: add `def pin_matches_model() -> bool` comparing `PINNED_COMMIT` with `vendor.VENDORED_COMMIT` by prefix (the registry pin is short, the vendor pin full). Also expose `RETIRED_V3 = not pin_matches_model()`.
2. `src/ybcal/cli.py`: in the dispatcher for `recommend`, `study`, `sensitivity`, `robust`, `report` and `fees`/`seats` when they emit a lock-relevant table, exit 2 with the message "the parameter registry is pinned at ycash6 7702d22 (v3, retired); the model is at <vendor pin>; this run is not a release input — re-pin the registry (D-MP-1) or pass --allow-retired-v3" while `RETIRED_V3`, unless `--allow-retired-v3` is given. Also refuse while `examples.reference_param_drift()` is non-empty (auditor fix 4), with the drift listed.
3. With `--allow-retired-v3`: `report/build.py` puts a banner as the first line of `report.md`/HTML ("v3 parameter set (retired, ycash6 7702d22) — not a release input"), adds `"retired_v3": true` and `"release_input": false` to `recommended.json` beside `"pin"` (`:1061`, `:1162`), writes the patch header "against the retired v3 params.cpp (ycash6 7702d22); does not apply to the release line", and replaces "move off the shipped set" / "equals the shipped SetCommon()/MainParams() values" (`:936-940`, `:1241`) with "…the v3 set at 7702d22". Strip `startHeight`/`enforceUntilHeight` 3,075,000 / 3,495,480 from `networks.main` (withdrawn, hardening F-5) or mark them withdrawn.
4. `lock_readiness` (`report/build.py:263-337`): add two **required** items before the others — "Registry pin is the release line's commit" (ok iff `pin_matches_model()` and, when a clone is given, `git merge-base --is-ancestor <pin> <release commit>` holds and `git diff <pin>..<release> -- src/yellowback src/vault src/consensus src/script src/main.cpp` is empty) and "Live `params check` at the release commit passes". Make "params.cpp patch applies" required and run it at the release commit (`emit.check_patch(…, commit=<release commit>)`), not at `PINNED_COMMIT` (auditor fix 3). Change "Every locked parameter has a recommendation" to iterate the **node's** field list from the live extraction when a clone is given (so an unregistered node field fails it), falling back to the registry with an explicit "registry-relative" note.
5. `docs/reports/2026-10-real/README.md` §7: add "- [ ] Registry and simulator re-pinned to the upgrade line (W4-K-1; until then this report calibrates the v3 set)". `README.md`: state the guard in the quick-start next to `make recommend`.

**Part 2 — the re-pin (branch `fix/W4-K-1-registry-repin`):**

6. Registry at the release commit (ycash6 `upgrade/vault`, at least `1310a41a1`; record the commit used): drop the 12 retired entries into a frozen `registry_v3.py` (kept so the published v3 reports stay reproducible), add the 26 node fields with honest classes — `issuedBeforeStart` `derived` (`CirculatingSupplyAt(startHeight − 1)`), `pqAddressVersion`/`attestorSetId`/`pqFalconHeight` `meta` (identity, never searched), `attestorCancelThreshold`/`attestorUnlockThreshold` `constant` (pinned, "not hashed"), `claimDelay`, `feeBands[*]`, `feeFloorCents`, `earlyRedeemFeeBps[*]`, `maxVaultShareBps`, `vaultShareFloorCents`, `residualMinCents`, the bond and seat fields `locked`. Extend `extract.py` for the shapes it now rejects (struct-array members `feeBands[i].uptoCents` / `.bps`, `std::vector<unsigned char>`, `uint256`, `N * COIN` products) — failing closed on anything else, as today. Regenerate `snapshot_<commit>.json`, `params_cpp_<commit>.json`, `docs/parameters.md`.
7. Every value then equals the node; `KNOWN_V3_REGISTRY_DRIFT` becomes `{}` and the test asserts emptiness. A field with no study is listed by lock-readiness as "owner value, uncalibrated" (pin it in `[owner_pinned]` with its D-* reference: D-IT-*, D-Q-*, U-23, 03/I-3) rather than silently passing. ## 6. Acceptance criteria

- Part 1: no lock-relevant command produces output from the v3 registry without the explicit flag; any such output is stamped "retired — not a release input" in the report, `recommended.json` and the patch; lock-readiness cannot print `lock-ready: yes` while the registry pin differs from the release line; the real-data report's §7 lists the re-pin.
- Part 2: the registry equals `Params` at the recorded release commit field for field and value for value (0 missing, 0 retired, 0 drift); `params check` at that commit passes; the patch check is required and runs there; D-MP-2 recorded.

## 7. Risks and side effects

- Published v3 reports (`docs/reports/2026-10-*`) must stay reproducible: keep `registry_v3.py`, the `7702d22` snapshot and `--allow-retired-v3`; reproduce instructions in each report gain the flag.
- The guard turns `make quick`/`make recommend` red on `upgrade/vault` until the re-pin lands — intended; say so in the PR and the README.
- No node, client or consensus impact. Values derived after the re-pin may disagree with owner-set node values; those disagreements go to the owner as decisions, never as direct node edits (workspace rule: a constant changes in `ycash-dd`/`ycash6` only with the calibration result that justifies it).

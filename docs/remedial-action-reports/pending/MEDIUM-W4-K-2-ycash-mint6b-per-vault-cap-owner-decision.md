## 1. Finding

The fees study recommended `maxVaultShareBps` = 1,000 (10 % of the MINT-6 cap, floor $10,000) as the guard against unliquidatable whale vaults, reasoning that MINT-6 caps against coinbase issued since the start height ($39,420 after a year at $0.40), so $100,000 vaults would be "class-C-only for the first years" and the share "never binds below H-12's scale". The owner then moved MINT-6's base to the **circulating** supply (D-Q-25) and wrote "the per-vault share limit (10 %, floor $10,000) stands" (`yellowback-quantum-plan.md:131`) — but the study was never re-run on that base. On the shipped base (16,972,537.5 YEC at height 3,062,423; 15 % = 2,545,880.6 YEC of cap), MINT-6b allows a vault larger than the largest claim the measured books can absorb ($34,675, p50 whole visible bid book; $25,815 at p10) at any price above **$0.1362**, and it stops binding below `maxMint` ($100,000) at **$0.3928**. At $0.40 every class can mint a $100,000 vault from the activation block; if it goes under θ its claim must sell ≈ $125,000 of YEC into a book of ≈ $5,000. The node's own comment (`params.cpp:22-24`) names "MINT-6b's per-vault share" as one of the three bounds that make D-Q-24's reversal of H-12 acceptable; at realistic prices that bound is illusory.

W4 03/new-3 compounds it for class C: MINT-6 refuses a mint over the aggregate cap only when the class base ratio is below `recapRatioBps`, and class C's base (50,000) equals it, so the aggregate cap never refuses a class C mint. Once MINT-6b stops binding (≥ $0.39), a class C vault is bounded only by `maxMint` per vault, and class C in aggregate only by HALT-2 (global ratio 200 %). The fees spec already lists "class C stays outside the aggregate cap" as an open owner item. Loss scenario: a whale mints $100,000 (or several $100,000 class C vaults under distinct keys — MINT-6b is per vault, not per owner), the price falls through θ, and no claimant can execute; the shortfall is bad debt of the system. Bounded per vault by `maxMint`, needs a further fall after θ, no mainnet height is set — hence Medium — but the decision's stated premise is false and should go back to the owner now.

## 3. Fix options considered — for the owner

"Exceeds depth" = the price above which one vault can exceed the $34,675 executable claim (p50 whole visible book, 2026-10-04 books; $25,815 at p10). The supply grows ≈ 657,000 YEC/yr (3.9 %) until the halving at 3,960,000, so every crossover price falls ≈ 3.9 % a year.

- **O1 — lower `maxVaultShareBps`** (value change only; no new field, no new state). 340 bps reproduces the $34.6k bound at today's $0.40. Weakness: a share of the cap scales with price while book depth in dollars does not necessarily, so the bound re-opens as YEC rises (O1b exceeds the p50 depth again above $0.40 and reaches $100,000 at $1.16) and drifts with supply growth. Good if the owner wants the bound to follow market cap on purpose.
- **O2 — an absolute per-vault dollar cap tied to measured depth** (new `Params` field, e.g. `maxVaultCents`, MINT-6b becomes `min(max(share·cap, floor), maxVaultCents)`): the shape the auditor and the verifier prefer, because it tracks what actually limits a claim (dollar depth). Calibrated by yb-calibration from the depth series per release ($25,000 for p10, $35,000 for p50 at today's books); changing it is a consensus constant change each time. Keeps `maxMint` = DigiByte's $100,000 (D-Q-24) as the protocol ceiling and `maxOutput`.
- **O3 — lower `maxMint`** to the depth bound (≈ $35,000; or $25,000 at p10). Same effect as O2 with no new field, but partly reverses D-Q-24 ("DigiByte's maxMintAmount restored") and also limits the RPC/wallet ceilings that read `maxMint` (`state.cpp:349`, `txbuilder.cpp:1181`, `rpc/yellowback.cpp:722`, `:1673`).
- **O4 — keep 1,000 bps with a recorded rationale**: the owner accepts single vaults up to $100,000 at any price ≥ $0.39 (the D-Q-24 "depth bet"), and the record is corrected: `params.cpp:22-24`, quantum plan `:388-393` and D-Q-25 must stop citing MINT-6b as a per-vault bound at realistic prices, and the release notes state the per-vault exposure.
- **Class C (W4 03/new-3), decided in the same ruling** (fees spec `:532-533` alternatives): (C-i) keep class C outside the aggregate cap (W20 design) — then O2/O3 is what bounds a class C vault, and class C's aggregate is bounded only by HALT-2; (C-ii) apply MINT-6 to every class (drop the `< recapRatioBps` clause, i.e. the recap tier loses its "soft cap"); (C-iii) a separate, higher aggregate cap for the recapitalisation tier (new field). Any of O1–O3 bounds class C **per vault**; only C-ii/C-iii bound it in aggregate.

**Auditor/verifier recommendation, carried here:** O2 (or O3 if the owner prefers no new field) at the p50 whole-book depth, revisited per release from the depth series; plus an explicit class C ruling. Note the asymmetry for later changes: lowering a per-vault bound after activation is a tightening (old nodes still accept every mint new nodes accept), raising it is a loosening that every node must adopt — so starting low costs an upgrade to relax later; starting high costs a coordinated tightening.

**Rule-4 four-part check (for a node PR under O1–O3).** DigiByte does **X** = cap one mint at `maxMintAmount` $100,000, in **Y** = `ref/digibyte/src/digidollar/` (consensus params), using **M** = a fixed dollar per-mint ceiling with no reference to market depth (DigiByte's liquidity is not the binding constraint). The Ycash equivalent **Z** = MINT-2 `maxMint` plus MINT-6b's share of a price-scaled cap (`state.cpp:412-415`), which lacks a depth-scaled bound and scales with price. So the adaptation **W** = (O1) a smaller share, or (O2) a dollar `maxVaultCents` beside the share, or (O3) a smaller `maxMint`. **In-tier ladder:** a module constant (O1/O3) is the lowest rung; O2 adds one module parameter and one clause, no new state, no primitive change; nothing touches `src/vault/`, `src/script/`, `src/consensus/`.

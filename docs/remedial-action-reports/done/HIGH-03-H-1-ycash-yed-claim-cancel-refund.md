## 1. Finding

A YED claim is consensus-valid when it lands: RED-4 decides underwater-ness, RED-2 forces the claimant to burn the vault's whole debt (`mintedCents`) at the claim block (`ycash-dd/src/yellowback/state.cpp:1290-1293`, `totals.supplyCents -= burned`). The claim's collateral sits in a claimant intent that the attestor set — the vault's `cancelSetId` *is* `attestorSetId` (`src/yellowback/script.cpp:86-87`, enforced by `Module::ValidateCreate`, `src/yellowback/module.cpp:65-70`) — may cancel for `delay` = 576 blocks with `cancelThreshold` signatures (the cancel branch `<cancelSetId> OP_2 OP_CHECKSETSIG`, `src/vault/template.cpp:211`). The primitive's I-2 asks for nothing but "before `delay`, one output ≥ the intent's value back to `vaultHash`" (`src/vault/state.cpp:539-546`); the module's `ApplyIntentSpend` then re-creates the vault ACTIVE at `cancel:0` with the full `mintedCents` and `burnedCents = 0` (`src/yellowback/state.cpp:795-843`, `:833`) and **does not credit `supplyCents`**. The claimant's YED, worth the whole debt, is destroyed; the claimant can only try again by burning the debt a second time.

Nothing deters the canceller. `RefusedAttestorSetAct` (`src/yellowback/state.cpp:1922-1940`) and `Module::CheckBlock` (`src/yellowback/module.cpp:110-118`) make every `SET_WINDDOWN` and every non-self `SET_REMOVE` of the attestor set block-invalid, so the primitive's cosigned slash (`src/vault/state.cpp:796-835`) cannot reach the attestor set at all; `SET_EQUIVOCATION` (`:837-860`) needs two set signatures over one outpoint, which a canceller never produces; U-19 makes the cancel signature "not an act", so consensus does not even record who cancelled. Every fixture and the plan's own table put `cancelThreshold` at 1 (`src/test/yellowback_state_tests.cpp:179-182`; upgrade plan line 358 "1 of 15"), and `AdoptedSet` (`src/yellowback/module.cpp:40-48`) does not check it (I-3). **Scenario A:** a vault owner who holds one attestor seat (bond returned 14 days after exit) cancels every claim on its own underwater vault for the price of a network fee; each claimant loses debt-worth YED; the bad debt stays in the system. **Scenario B:** any one of 15 bonded parties (or one compromised attestor key) griefs claimants at will. Certain, unbounded, zero-marginal-cost loss for claimants; the liquidation mechanism is switchable off by one party. The verifier traced it to two owner decisions four days apart that were never reconciled: D-U3 (2026-10-07, "a cancelled wrong-price claim forfeits its burn") was taken while §3.6/§11 still had the contested-cancel slash; D-Q-29 (2026-10-11, commit `64ee838`) removed every removal-by-vote from the attestor set without revisiting D-U3. Identical on `ycash6` (`src/yellowback/state.cpp:795`, `:833`, `:1293`, `:1922`; `src/yellowback/module.cpp:82-83`).

## 2. Root cause

At `ycash-dd` `055d9c2` / `ycash6` `e866c45` (line numbers identical unless noted):

- `src/yellowback/module.cpp:40-48` — `AdoptedSet` pins OPEN, `seats`, `maturity`, `livenessWindow`; not `cancelThreshold` / `unlockThreshold` (I-3).
- Plan: `docs/plans/yellowback-upgrade-plan.md:1002` (D-U3), `:1189` (U-23/U-24 "The cancelled claimant's burn is not refunded"), `:401-411` (§3.6 "A contested cancel … is resolved by `slashThreshold` signatures"), `:688` (§11 row "One watcher cancels repeatedly → `SET_REMOVE` by `slashThreshold`"), `:358-359` (cancel/slash thresholds); `yellowback-quantum-plan.md:135` (D-Q-29 "never shrinks by vote … EQV-1 slashing is the only removal"), `:137` (D-Q-31 "a cosigned slash vote still lands on a member that already left" — false for the attestor set); `yellowback-in-term-claims-plan.md:88` (D-IT-13 "the claimant's exposure").

## 3. Fix options considered

| | Option A — **refund the burn on cancel** (module rule on the cancel transaction) | Option B — stake-bearing cancel | Option C — restore a cosigned slash for cancels |
|---|---|---|---|
| Mechanism | The cancel must carry a YED token output of the claim's `burnedCents` to the holder the burned YED came from; the module creates the token and credits `supplyCents`. A cancel then costs the claimant nothing: the attacker can only delay (≤ 576 blocks per round), never destroy. | The cancel is valid only with a bond-sized output locked for `delay`, forfeited to the claimant if the vault is claimed again within N blocks at a price that still satisfies RED-4. | Lift the module's refusal of `SET_REMOVE burn=1` for a member key that signed a cancel in the last `delay` blocks (the primitive path exists). |
| Consensus footprint | Module only (`src/yellowback/`): one new rule on an existing transaction shape (I-2 cancel), one appended record field. No primitive, opcode, template or `main.cpp` change. | Module *and* primitive: consensus must record the canceller (03/V-2 — today it is not indexed), a new locked-output shape, an adjudication rule ("the claim was valid") with its own price reading, and a forfeiture path. New state, new act or template branch. | Primitive act rules unchanged, but the module must record the canceller (03/V-2) and a per-key "recent cancels" table, and re-open D-Q-29 for one act type. |
| State / undo | `IntentRecord` gains `refundScript` (append-last, SERIALISATION.md §1); a `Token` record on the cancel's refund output; `Totals.supplyCents` credited. All through `OverlayStateView`/`UndoRecord` — no new undo code. `SCHEMA_VERSION` 12 → 13. | New records (stake, adjudication), new undo semantics, new RPCs. | New per-key records; the slash *burns* the bond — the claimant is still not made whole. |
| Golden / vectors | `yellowback_golden.json` regenerates (the `cancel5` block gains a refund output; the Intents preimage grows). `vault_vectors.json` **unchanged** (no primitive change). | Both golden and (if a template branch) `vault_vectors.json`. | Golden only. |
| Plan edits | D-U3 revised; U-23/U-24; §3.6 and §11 rows annotated for the attestor set; D-IT-13 wording. | As A plus a new §3.4 sub-rule and D-Q-29 carve-out. | D-Q-29 re-opened; §3.6 restored for one act. |
| What it gives up | The forfeit as a deterrent against *gamed* claims (the claimant picking 4–6 of 6 attestations). The canceller pays a dust output + fee. A 576-block carry-over of a pre-Falcon holder across the Falcon boundary (see §4 step 3). | — | The claimant's loss stands; only the attacker is punished, by a 7-of-15 vote the attacker may be part of. |
| Verdict | **Recommended.** Removes H-1 and M-1 (03/M-1's supply drift is exactly the missing credit) with the smallest consensus footprint; needs no primitive change and no owner re-ruling on D-Q-29. | Rejected: largest footprint; needs an in-consensus notion of "the claim was right", which RED-4 already is. | Rejected as the primary fix: does not refund the claimant, re-opens an owner decision, and punishes by vote. May be added later as a deterrent if the owner wants the forfeit back in some form (then **conditional**, never free). |

The first-wave text of option A ("a YED token of `mintedCents` to the intent's recipient hash") is not implementable as written: the claimant intent carries only `SHA256(recipient script)` (`src/vault/template.cpp:207`), so a canceller cannot build an output to it; and the amount must be the whole `burnedCents` (the debt plus any sub-dollar remainder the claim burned, `state.cpp:1291`), not `mintedCents`. §4 fixes both.

**Rule-4 four-part check (for the PR body).** DigiByte does **X** = make a DigiDollar liquidation final at inclusion, in **Y** = `ref/digibyte/src/digidollar/` (validation-time rules), using mechanism **M** = no post-inclusion challenge window (there is no attestor cancel in DigiDollar). The Ycash equivalent **Z** = the vault primitive's cancel branch (I-2, `ycash-dd/src/vault/state.cpp:539-546`; upgrade plan §3.4), which gives a bonded set a 576-block veto over a consensus-valid claim and therefore lacks **M**. So the adaptation **W** = a module rule on the cancel transaction (CAN-1 below) that makes the veto value-neutral for the claimant: the burn the claim destroyed is re-issued to the holder it came from and `supplyCents` is credited, so a cancel delays a liquidation and never charges for it.
**In-tier ladder answer.** Tier 3 is decided (R3/O-1). Within it: a **module rule** (not the primitive — the primitive stays application-agnostic and already provides everything the rule needs), over the **existing template branch** (no new opcode, no transaction field), with **per-vault state** (one appended field on the claimant's intent record; no global table). Why no cheaper rung: a wallet or policy change cannot re-issue consensus-burned supply; a primitive-level record of the canceller (option C) is a bigger footprint and still leaves the claimant unpaid.

## 4. Recommended fix (option A)

Name the rule **CAN-1** (the module's cancel rule; U-24 revised). Land on both lines in one PR per repo, same commit sequence.

1. **Record the refund holder at the claim** — `src/yellowback/state.cpp`, `ApplyVaultSpend` (`:703-779`): when the spend is a claim (`!ownerPath`), set on the **claimant** `IntentRecord` a new field `refundScript` = the `scriptPubKey` of the YED token spent by the claim's lowest-index YED input (`log.spentTokens[0].scriptPubKey`, filled at `:1115-1124` in vin order). RED-2 guarantees `yedIn ≥ mintedCents > 0`, so `spentTokens` is non-empty on a held claim; keep the explicit guard (`VAULT_SPEND_MALFORMED` if empty). The residual intent's `refundScript` stays empty.
   - `src/yellowback/view.h:603-620` — append `std::vector<unsigned char> refundScript` **last** in `IntentRecord::SerializationOp` (SERIALISATION.md append rule); bump `SCHEMA_VERSION` 12 → 13 at `view.h:84` with a one-line reason (an older directory is wiped and rebuilt). The `I` table is already in the state-hash order (`view.cpp:455`), so no new table.
2. **The cancel rule (CAN-1)** — `ApplyIntentSpend` (`:795-843`), cancel branch, after the `relock != 0` check (`:826`):
   - let `refund = vault->burnedCents` (the CLAIMING record's burn, `:1296`) and `holder = in.record.refundScript`; both must be non-empty/non-zero, else verdict `INTENT_CANCEL_NO_REFUND` (a CLAIMING record from before this rule cannot exist on a chain that activates with it — regtest/devnet are wiped; there is no mainnet state);
   - find `j` = the **lowest** output index `≥ 1` with `tx.vout[j].scriptPubKey == holder`; none → `INTENT_CANCEL_NO_REFUND`. Any `nValue > 0` is accepted (the token rides on an ordinary carrier, as every YED output does); the output is not an intent, a vault, an act or the OP_RETURN (a cancel carries no payload — `:801` already refuses one);
   - write `TokenRecord{cents = refund, nValue = tx.vout[j].nValue, scriptPubKey = holder, height = ctx.height}` at `keys::Token(COutPoint(txid, j))` (as `:723-730` does for assignments), append it to `log.assigned` and set `log.yedOut = refund` (so IN-3 accounting and `yed_gettxinfo` show the re-issue);
   - `totals.supplyCents += refund` (this is the 03/M-1 fix), then the existing `v.burnedCents = 0` (`:833`).
   - `src/yellowback/state.h:112-117` / `state.cpp` verdict table: add `INTENT_CANCEL_NO_REFUND` = `"intent-cancel-no-refund"` (block verdict `bad-yellowback-intent-cancel-no-refund` through the existing prefix).
3. **TOK-PQ.** The refund output is exempt from `HolderAllowed` (`state.cpp:537`, `:595`): it is the holder that legally held the YED at the claim, at most 576 blocks earlier. Record in the spec that a holder that was allowed at the claim may receive the refund across the Falcon boundary (given up; bounded by `delay`). Do **not** apply TOK-PQ here — it would make every cancel of a claim that straddles the boundary impossible, i.e. re-open the forfeit.
4. **Pin the thresholds (03/I-3)** — `src/yellowback/params.h`: add `int attestorCancelThreshold` (ATTESTOR_CANCEL_THRESHOLD = 1 — the plan's §3.4 table) and `int attestorUnlockThreshold` (= 1, same table; UNLOCK is refused on a YED V by `ValidateSpend` anyway) as consensus constants beside `attestorSeats` (`params.h:243`, **not** in `ParamsRecord` — follow `attestorSeats`' precedent, so no hash change); `AdoptedSet` (`module.cpp:40-48`) refuses a set whose `cancelThreshold`/`unlockThreshold` differ. Mirror in `yellowback_model.py`'s adoption check. `-yellowbackattestorset` sets created with other thresholds are then not adopted (every fixture already uses 1/1/1).
5. **Builders.** The primitive's `vault_buildcancel` (`src/rpc/vault.cpp:1567-1650`) is module-agnostic and would now build a cancel the module rejects — and a member who signs it burns its sign-once slot for that prevout (see MEDIUM-01-V-2). So:
   - `vault_buildcancel` refuses an intent whose `tag == YED\0` with `RPC_INVALID_PARAMETER` "a YED claim intent is cancelled with yed_buildcancel" (one `if` before the build);
   - new `yed_buildcancel "intentoutpoint"` in `src/rpc/yellowbackwallet.cpp`: same body as `vault_buildcancel` (share the helper; keep the byte-identical rebuild cache keyed by intent) with `vout[0]` = re-lock, `vout[1]` = `{holder, the wallet's standard YED carrier value}` where `holder` is read from the index (`IntentRecord.refundScript` of the claimant intent) and the amount is `burnedCents` for display; then `Fund`. Result adds `"refund": {"vout": 1, "script", "cents"}`. `set_signcancel` is unchanged (it reads `cancelSetId` from the I script).
   - `yed_getvault` (`src/rpc/yellowback.cpp:254`, next to `burnedCents`): add `refundHolder` (hex script) for a CLAIMING vault, listed as OPTIONAL in `doc/yellowback-rpc-contract.json` (`yellowback_rpc_contract.py:163-169` flags undeclared extras); follow `doc/yellowback-rpc.md`'s versioning rule for an additive optional field (if it requires an `rpcversion` bump, note the lightwalletd 8 pin — 06/L-1).

## 6. Acceptance criteria

- A cancel without the refund output is block-invalid on both lines; with it, the claimant holds `burnedCents` of YED and `supplyCents` is credited (03/M-1 gone).
- `AdoptedSet` refuses an attestor set whose `cancelThreshold`/`unlockThreshold` differ from the constants.
- `vault_buildcancel` refuses YED intents; `yed_buildcancel` builds a valid cancel; no member can sign a doomed cancel through the node's RPCs.
- Golden hash regenerated in a separate commit with a reviewer recomputation; `SCHEMA_VERSION` 13; `yellowback_golden.json`, `yellowback_model.py`, `SERIALISATION.md` identical on both lines.
- Plans and `make spec` output updated as in §4 step 8; `docs/mapping.md` row added.
- PR body carries the four-part check and the in-tier ladder answer above; two independent reviewers (review gate, workspace rule 2) — `src/yellowback/` is not in the gate's frozen list, but this is a consensus rule and goes through the gate by the owner's standing instruction for module rules.

## 7. Risks and side effects

- **Chain split:** none on public networks (no activation height anywhere); on regtest/devnet every existing chain is wiped. Both lines must land together; a line that cancels without the refund rule would accept a block the other rejects.
- **Vector freeze:** `vault_vectors.json` does not change; the golden does — land before P8 freezes the golden.
- **Sign-once interaction (MEDIUM-01-V-2):** an attestor who signed an old-shape cancel after this rule would burn its sign-once slot for that prevout; the `vault_buildcancel` refusal (step 5) is the guard. Deploy the tooling with the node.
- **Economics:** the forfeit's deterrent against gamed claims goes away; the remaining cost of a gamed claim is the YEC fees and the claimant's delay, and the attestors keep their 576-block veto. If the owner wants a deterrent, add option C later as a *conditional* slash — never restore the free forfeit.
- **Clients:** additive `yed_getvault` field; YEW/chain-viz unaffected unless the contract rule forces an `rpcversion` bump.

## 1. Finding

`SetSigChecker::CheckSetSigs` (`ycash-dd/src/vault/checker.cpp:28-41`) computes `sighash = SignatureHash(scriptCode, tx, nIn, SIGHASH_ALL, amount, branch)` (`:34`) and the set message `SetSigMsg(setId, role, prevout, sighash)` (`src/vault/act.cpp:325-338`). `SIGHASH_ALL` commits to **every input**, so the members' signatures commit to the ordinary coins that pay the fee — coins the builder's wallet chose (`Fund`, `src/rpc/vault.cpp:716-748`: wallet P2PKH inputs, a fresh change key, `LockCoin` at `:748` in memory only) and that S-2/I-1/I-2 *require* to be external (`src/vault/state.cpp:518`, `:536`, `:542`). `SET_EQUIVOCATION` (`src/vault/state.cpp:837-860`) ejects and freezes any member with two signatures over one `(setId, prevout)` and different `(role, sighash)` — a sighash is 32 opaque bytes; nothing about either transaction's validity is weighed. The node wallet's sign-once record (`src/rpc/vault.cpp:1459-1486`, written before the first signature) and Hawkeye's mirror (`hawkeye/crates/hawkeye-store/src/signonce.rs`) fail closed, so no honest member is *forced* to equivocate; what remains is: once a fee input of the signed transaction is spent (the builder double-spends its own coin, a restart loses the `LockCoin` and an ordinary send takes it, `lockunspent false`), the signed unlock/cancel is unconfirmable **and every member who signed it can never sign another spend of that prevout**. For an UNLOCK the vault waits for `ownerHeight`; for a CANCEL the intent RELEASEs after `delay`. In the YED shape (`setId = cancelSetId = attestorSetId`, any claimant may APP-spend) one malicious attestor who coordinates the cancel and then spends its fee coin vetoes a cancel that `cancelThreshold` honest members were willing to make — unless enough *unsigned* members remain to build a fresh one.

Aggravation (07/N-2): `vault_buildunlock` (`src/rpc/vault.cpp:1514-1543`) has no rebuild cache — every call draws a new change key (`NewWalletKey()` in `Fund`, `:716-748`) and, because the previous coins are `LockCoin`ed, other inputs; two ordinary calls yield two sighashes for one prevout. On one wallet the sign-once record refuses the second; on a restored or mirrored wallet (MEDIUM-07-F-5) the second is signed and slashable. `vault_buildcancel` has an in-memory cache (`g_cancelBuilds`, `:640-643`, reuse rules `:1619-1636`) that a restart loses. **The first-wave remedy "self-fund the unlock from the vault's value" is consensus-illegal** — S-2 is `sumI + sumRelock ≥ tcoin.value` (`state.cpp:518`), I-1/I-2 need an output ≥ the coin's value (`:536`, `:542`): the fee **must** come from other inputs. Do not carry it forward. Identical on `ycash6` (`src/vault/checker.cpp:34`, `src/rpc/vault.cpp:1465`, `:1487`).

## 2. Root cause

- `src/vault/checker.cpp:34` — the hashtype is `SIGHASH_ALL`; `src/vault/checker.h:39` documents it; `src/rpc/vault.cpp:1447` (`SignSetInPlace`) mirrors it for the wallet; `qa/rpc-tests/test_framework/vault.py:974-978` (`template_sighash`) and `:1800` (`_check_set_sigs`) for the model; `gen_vault_vectors.py:50`, `VAULT_VECTORS.md:48` for the vectors; `src/test/vault_vectors_tests.cpp:391` for the C++ replay; `hawkeye/crates/hawkeye-core/src/attribution.rs:5-14`, `:109-118` recompute the same digest to attribute a spend's signatures.
- `src/rpc/vault.cpp:1514-1543` — no memo of the last unlock build per vault outpoint; `:640-643` the cancel memo is in memory only; `:716-748` `LockCoin` (`:748`) is in memory only.
- `doc/vault-rpc.md:285-291` (`vault_buildunlock`), `:294-304` (sign once), `:306-320` (cancel rebuild "remembered in memory until restart") — nothing about the fee coins or "call once".

## 3. Fix options considered

1. **`SIGHASH_ALL | SIGHASH_ANYONECANPAY` in `CheckSetSigs` (recommended).** ZIP-243 with ANYONECANPAY commits to this input's prevout, amount, sequence and scriptCode, every output, `nLockTime`, `nExpiryHeight`, `valueBalance` and the shielded components, and omits `hashPrevouts`/`hashSequence` of the other inputs (`src/script/interpreter.cpp:1193-1215`, `:1397` — already implemented for ECDSA). `SetSigMsg` already binds the outpoint; S-1 allows one template input; so the only thing a third party can change is which ordinary coins pay the fee. A re-funded transaction has the **same** sighash → the recorded signature is reused (`:1470`, idempotent) → no equivocation exists. Verifier: "sound".
2. **A set message over `(setId, role, prevout, hashOutputs, amount, branch)`** without touching the hashtype. Same property, but a second digest construction to specify, vector, and mirror in three languages. Rejected in favour of (1), which reuses ZIP-243 verbatim.
3. **Spec-only: fund a cancel only from the signers' own coins + wallet refusals.** Does not remove the veto when the funder is the malicious member. Rejected.
4. **Self-fund from the vault value.** Consensus-illegal (S-2, I-1, I-2). **Rejected; must not be implemented.**
5. **Persist the builds** (wallet-DB memo of the last unlock/cancel build and its coin locks) — not an alternative but a complement: it closes N-2 on the honest-mistake side and is needed for restart safety regardless of (1). Taken.

**Rule-4 four-part check (PR body).** DigiByte does **X** = nothing equivalent (DigiDollar has no threshold-set covenant; its signatures are per-key Tapscript/BIP342 checks) in **Y** = `ref/digibyte/src/script/interpreter.cpp`, using mechanism **M** = the BIP341/BIP342 sighash with its `SIGHASH_ANYONECANPAY` flag. The Ycash equivalent **Z** = ZIP-243 `SignatureHash` (`ycash-dd/src/script/interpreter.cpp`), which has the same flag with the same semantics (only the signed input's prevout/sequence/amount/scriptCode, all outputs). So the adaptation **W** = the set-signature checker computes the ZIP-243 digest with `SIGHASH_ALL | SIGHASH_ANYONECANPAY`; `SetSigMsg` is unchanged; equivocation stays "two different spends of one outpoint".
**In-tier ladder answer.** Tier 3 stands. Within it: the **existing opcode's checker** (no new opcode, no template change, no transaction field, no state). Why no cheaper rung: a wallet-only change (persisting builds) leaves the builder's veto, which only a digest that excludes the fee inputs removes; a spec rule about funding (option 3) is unenforceable.

## 4. Recommended fix

1. **Consensus** — `src/vault/checker.cpp:34`: `SIGHASH_ALL` → `SIGHASH_ALL | SIGHASH_ANYONECANPAY`; `checker.h:39` comment. `ycash6/src/vault/checker.cpp:34` the same (its `SignatureHash` takes `*txdata`). Nothing else in `src/vault/` or the interpreter changes: `OP_CHECKSETSIG` passes `scriptCode` and `consensusBranchId` through (`interpreter.cpp:1036-1051`), `SetSigMsg` is untouched, the equivocation act (`state.cpp:837-860`) is untouched.
2. **Wallet signer** — `src/rpc/vault.cpp:1447` (ycash6 `:1465`): the same hashtype in `SignSetInPlace`; the sign-once record keeps `(role, sighash)` — with the new digest a re-funded build has the same sighash, so re-signing is the idempotent path (`:1468-1476`). Hawkeye signs through `set_signunlock`/`set_signcancel` (`hawkeye-ycash/src/client.rs:351-362`) and stores the node's bytes (`signonce.rs`, `ycash-unlock`/`ycash-cancel`) — **no change to its signing path**; its *attribution* (`hawkeye-core/src/attribution.rs:109-118`, which recovers signer keys from `SetSigMsg(…, sighash)`) must switch to the new hashtype or it stops attributing every real spend.
3. **Re-funding without re-signing** — new RPC `vault_refee "hex"` in `src/rpc/vault.cpp` (wallet): takes a built transaction (unlock or cancel) whose template input may already carry set signatures, drops every non-template input and the change output, re-runs `Fund`, keeps `vin[templateIdx].scriptSig` verbatim (the signatures stay valid under ANYONECANPAY) and returns the new hex + the unchanged `sighash`. Document that anyone may re-fund: the signatures bind the outputs and the template input only.
4. **Idempotent builds (07/N-2)** — `vault_buildunlock`: a build memo keyed by the vault outpoint, reused byte-identically while its fee inputs are unspent and not in `mapNextTx` (the rules at `:1619-1636`), with an explicit `rebuild: true` parameter to force a new build (only sensible before anyone signed). Move both memos (`g_cancelBuilds`, the new unlock memo) and `g_recipients` (`:640`) into the wallet DB (`CWalletDB` records `vaultbuild` keyed by outpoint, `vaultrecipient` keyed by hash) so a restart keeps them; re-`LockCoin` the memo's inputs at wallet load. Document "call once" in `doc/vault-rpc.md:285-291`.
5. **Vectors** — `gen_vault_vectors.py`: `template_sighash(…, hashtype=SIGHASH_ALL|SIGHASH_ANYONECANPAY)` for the `spends[]` section only (`:413`, `:468-485`); `ownerSpends[]` (`:436-459`) keep the owner's own hashtype byte `SIGHASH_ALL` on the PQ signature — **do not change OP_CHECKPQSIG's hashtype** (quantum spec; YEW signs it); `setSigMsgs[]` use synthetic sighashes and do not change; `_schema` line 50 and `VAULT_VECTORS.md:48` say the new hashtype. Regenerate `src/test/data/vault_vectors.json` (only `spends[0..1]` change: `sighash`, `setSigMsg`, `sigs`, `scriptSig`, final `tx`); `vault_vectors_tests.cpp:391` (`template_spends`) uses the new hashtype; copy byte-identical to `ycash6/src/test/data/`, `hawkeye/crates/hawkeye-core/tests/data/` (update the stamp in `attribution.rs:1-3`), and `yew/core/tests/vectors/` (with R8's re-copy; YEW's tests read `ownerSpends`, unaffected by this change).
6. **Model** — `qa/rpc-tests/test_framework/vault.py:974-978` `template_sighash` gains a `hashtype` parameter; `_check_set_sigs` (`:1800`) passes the new one; `script.py` already implements ANYONECANPAY (`:845`, `:904-907`).
7. **Spec** — `yellowback-upgrade-plan.md` §15.2 checker interface: "sighash = SignatureHash(scriptCode, tx, nIn, SIGHASH_ALL|ANYONECANPAY, amount, branch)"; §15.5 (60)/(70) findings: fee inputs may be replaced by anyone without a new set signature; `doc/vault-rpc.md` "Sign once" paragraph (`:302-304`): the record is keyed by `(setid, prevout)` and holds `(role, sighash)`; a re-funded transaction has the same sighash; `vault_refee`; `doc/vault-rpc-contract.json` entries. `docs/mapping.md` §22 row ("ZIP-243 ANYONECANPAY for set signatures; why not a bespoke digest"). **State explicitly in the doc and the plan: the fee is never taken from the vault's value (S-2, I-1, I-2).**

## 7. Risks and side effects

- **Chain split:** every set signature made before this change is invalid after it (`SCRIPT_ERR_SETSIG`); both lines land together; regtest/devnet state is wiped; no public activation height exists. Any Hawkeye or devnet instance must be redeployed with the matching node.
- **Vector freeze:** `vault_vectors.json` changes — land **before P8** freezes it; after P8 this would be a new network upgrade.
- **Malleability:** third-party txid malleability of template spends by input replacement — already present via the selector/extra-push case (01/V-4); chained unconfirmed template spends (a pre-built cancel of a mempool intent, finding (65)) must be rebuilt if the parent is re-funded. Document.
- **Hawkeye:** attribution must change in the same window or every spend attributes to nobody (alarm noise, no fund risk).
